# Asset Boundaries

## 六类资产

| 类型 | 核心问题 | 应包含 | 不应包含 |
| --- | --- | --- | --- |
| Context | 我们知道什么？ | 事实、约定、来源、时效、未知 | 执行步骤、工具实现、秘密 |
| Skill | 一类任务怎么稳定做好？ | 触发条件、输入、方法、输出、检查、失败处理 | 一次性事实、跨部门编排、API 参数 |
| Workflow | 一次业务流怎么运行？ | 触发、状态、步骤顺序、角色、Gate、产物流向 | 具体文案技巧、底层 API 实现 |
| Tool | Agent 能做什么动作？ | 输入/输出合同、权限、副作用、错误 | 业务判断、品牌策略、审批决定 |
| Human Gate | 哪些决定必须由人承担？ | 审批角色、审批包、有效范围、记录 | 模糊的“必要时确认” |
| Eval | 怎样证明能力合格？ | 固定输入、断言、禁错项、评分与回归 | 只写“效果不错”或单个成功案例 |

## 快速判断

- 事实会随活动、产品或团队变化：放 Context。
- 方法能跨多个同类任务复用：放 Skill。
- 涉及触发、多个 Skill、多人或等待审批：放 Workflow。
- 需要访问系统、读写数据或发布：做 Tool。
- 责任不能交给模型：设 Human Gate。
- 可以被明确判定对错或质量：写 Eval。

## Skill 粒度

一个 Skill 应产生一种主要 Deliverable，并具有一种稳定的质量定义。跨渠道、跨角色、跨审批的端到端任务通常是 Workflow，而不是一个巨大 Skill。

例如，“生成微信群直播提醒文案”可以是 Skill；“从活动创建到全渠道发布并复盘”必须是 Workflow。

## Context 与 Skill 的去重原则

品牌语气、受众、活动时间、嘉宾和产品事实只存 Context；Skill 通过稳定 ID 引用。不得把相同品牌说明复制进多个 Skill，否则会产生冲突版本。

## Skill 与 Tool 的去耦原则

Skill 描述意图与约束，例如“创建公众号草稿并返回预览”；Tool 承担认证、API、重试和错误。Skill 不保存 endpoint、token、临时 ID 或供应商私有参数。
