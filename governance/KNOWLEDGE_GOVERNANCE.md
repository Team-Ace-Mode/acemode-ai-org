# Knowledge Governance

## 目标

让 Agent 使用当前有效、来源明确、责任清楚的组织知识，同时保留原始业务系统的权威性和隐私边界。

## 知识流

```text
微信 / 腾讯文档 / 飞书 / AWS / GitHub / 人员访谈
  → Evidence Summary
  → 候选事实、决定、任务、分歧分别提取
  → Owner 确认
  → Context / Decision / Portfolio
  → Catalog 状态与复核日期
  → Agent 按任务最小读取
  → 变更或过期后更新、降级或归档
```

## 信息分类

| 信息 | 去向 | 规则 |
| --- | --- | --- |
| 稳定、跨任务复用的已确认事实 | `context/` | 有 Owner、source、状态、复核日期 |
| 方向、边界或责任变化 | `docs/decisions/` | 记录背景、选择、后果和复核条件 |
| 当前 Initiative 和下一 Gate | Portfolio / Leader Dashboard | 高频更新，不复制成长期方法 |
| 可复用执行方法 | `skills/` | 不混入一次性事实和账号配置 |
| 跨步骤业务编排 | `workflows/` | 明确触发、状态、角色和 Gate |
| 运行日志和原始聊天 | 原系统 / 日志系统 | 不进入长期 Brain；只提取经确认结论 |
| 密钥、Cookie、个人隐私、客户原始数据 | 安全存储 | 禁止进入仓库 |

## 微信 CLI 接入规则

微信 CLI 第一阶段只承担读取和证据整理：

1. 限定允许读取的群、时间范围和用途；
2. 保留群名、日期和可用的消息定位信息；
3. 区分事实、个人观点、正式决定、临时任务、分歧和旧决定；
4. 对个人信息和无关对话做最小化处理；
5. 输出 Evidence Summary，不直接修改 Active Context；
6. 由对应 Owner 审核后，通过 PR 更新 Context 或 Decision；
7. 不把原始聊天全文提交到 GitHub。

## 状态规则

- `draft`：来源已记录，但内容未由有权限的 Owner 确认。
- `active`：Owner 已确认，可用于当前决策和执行。
- `stale`：超过复核时间或权威来源可能已变化，只能作为线索。
- `archived`：历史信息，不进入默认上下文。

## 冲突处理

相同主题发生冲突时依次判断：

1. 是否存在更高权限的正式 Decision；
2. 哪一份来源更接近业务事实；
3. 哪一份经过对应 Owner 确认；
4. 哪一份更新时间和复核状态更有效。

仍无法判断时，将冲突写入 `brain/OPEN_DECISIONS.md`，由相应角色裁决。Agent 不自行合并矛盾事实。

## 复核频率

- 使命、原则和组织定位：每季度或发生方向变化时；
- 团队、角色和当前组合：每月；
- 品牌、渠道和产品事实：每月或发布重大变化时；
- 活动、价格、合作和临时任务：按事件有效期；
- 安全与权限：每季度及每次事故后。
